# 实例档案查询覆盖

## 结论与样本

`6390648110` 的本地 PG 与 Redis 差异中，确实有查询链遗漏的证据；但“本地缺失”也可能来自工程库已清理的历史版本、导入范围或 Redis 生成规则，最终原因以重新读取工程库为准。

此前预览的 **477 条缺失是分组内记录出现次数**。同一档案在 First/Second/Fourth Step 重复出现。合并分组后，按固定表的 **业务 ID + his_id** 统计，共 316 个版本，本地 PG 缺少 210 个版本：

## 已补充的查询链

适用入口：**实例查档案 → 工程环境 Voyage → bill_inmemory**。UDAL 和 `crmv3` 的原有链路保留。

1. 根 `prod_inst` 不再只取一条，保留同一 ID 的全部现存 `his_id` 版本。
2. `prod_inst_rel` 仅查询根实例 A/Z 两端的直接关系；关联产品读取实例、属性和账户，但不再展开它的关系或其他订购销售品。
3. 从根实例 `offer_prod_inst_rel` 取得直接销售品，读取这些销售品的双向一跳关系；关联销售品只读取实例、属性和定义，不再展开关系。
4. 不按关联销售品反查全部订购产品，避免经共享产品/销售品扩展到兄弟实例。关联集合循环去重。
5. 从 `prod_inst_acct.account_id` 查询 `account.account_id`；从 `prod_offer_inst.prod_offer_id` 查询 `offer_ces.offer_id`。两处字段是不同表的映射，保持销售品定义的 `offer_id` 不变。
6. 九张档案表批量按 ID 查询，以主键和 `his_id` 游标翻页，每页 500 行；不按状态或有效期过滤历史记录。
7. 查询结果与 INSERT 导出合并同表重复行，但保留不同 `his_id`。补全销售品关系主键、A/Z 端和账户的导出映射。

## 范围与状态

- 默认范围是根产品的一跳直接关系及根销售品的一跳关系，不是关系闭包，也不宣称与 Redis 快照范围完全一致。所有返回记录均来自工程库查询，不以 Redis 内容补造数据。
- 每类实例最多 100 个 ID，最多展开 8 轮，累计读取最多 5000 行。页面显示实际范围及截断原因。
- 销售品定义 `offer_ces` 为附加查询，每批最多 500 行；触达此边界时保守标记覆盖待核对，不据此宣称完整。
- 根记录存在且所有引用返回、无失败和截断时，表示**本次固定查询范围完成**，不是 Redis 各 Step 的精确快照一致性结论。
- 关系中引用的产品、销售品实例、账户或销售品定义未返回时，列出 ID 并标记“部分完成”。单个查询失败时保留其余成功结果。
- 部分结果的 INSERT 头部带警告。脚本仅预览/复制，不执行 PG 或 Redis 写入。
- `payment_plan` 与定价计划语义不同，仍不作为 `pricing_plan`；未确认的扩展表不加入此查询。

## 工程库复验

1. 重启本机工作台，连接工程 Voyage，在 `bill_inmemory` 执行实例 `6390648110`。
2. 检查“查询范围与覆盖”“关联引用未返回”和失败步骤；截断或失败时先排查对应分支。
3. 导出 INSERT，核对九张表的唯一 `ID + his_id`；尤其关注根实例历史版本、账户、关联产品属性和销售品关系。
4. 将新的工程结果与 Redis 样本按表、ID、历史版本比较。工程查询也未返回的版本，单列为“工程现存档案未返回”，再核对历史清理和缓存生成规则。
5. PG 导入、Redis 同步另行执行，本次查询补充不触发这两项写操作。

此前闭包夹具覆盖全部 316 个版本，但真实工程导出出现 3010 条产品关系：关联节点 `102460917` 又带出了约 2862 条关系。现默认改为直接关系边界，并增加不读取共享节点兄弟关系的回归验证。历史夹具的全覆盖结论不再适用于当前收紧范围；工程实际行数仍需重新查询核验。
